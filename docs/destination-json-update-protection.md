# 여행지 JSON 선택 업데이트와 필드 보호

## 관리자 사용 흐름

기존 `/admin/destinations/json-import`에서 **기존 여행지 업데이트**를 선택한다. 신규 등록은 기본 모드이며 이전 계약과 저장 경로를 유지한다. 업데이트 모드는 새로운 여행지를 만들지 않는다.

1. **JSON 파일 선택 및 자동 분석:** version 1 파일을 선택하면 바로 분석한다(1~30건, UTF-8 1MB 이하). JSON 원문은 기본 접힘이며 직접 입력·수정 또는 오류 후 재시도할 때만 `JSON 다시 분석`을 사용한다.
2. **여행지 확인 및 변경 내용 선택:** 국내 KTO contentId, 해외 Wikidata QID가 정확히 일치하면 업데이트 대상에 자동 포함한다. 이름·지역 후보는 각 후보의 `이 여행지로 업데이트` 버튼 한 번으로 관리자가 명시적으로 확정하며 비교 화면을 자동 갱신한다. 후보 선택·일치 확인·여행지 체크를 중복 요구하지 않는다. `key`는 행 식별자일 뿐 DB ID나 매칭 키가 아니다.
3. 실제 DB 값이 비어 있고 JSON에 유효값이 있으면 **자동 추가**로 기본 선택한다. 원하지 않는 자동 추가는 체크를 해제할 수 있다. 기존값과 다른 값은 **교체 여부 확인**에 기본 해제로 표시하며 같은 값은 **변경 없음**으로 접어 표시한다. 공통 선택 또는 여행지별 선택을 사용할 수 있고, **한 줄 소개와 상세 설명은 별도 체크박스**다. 번역 역시 언어와 name/shortDescription/description별로 선택한다.
4. 개별 항목·공통 항목 선택은 화면의 요약만 즉시 변경하며 서버 조회나 전체 행 재생성을 하지 않는다. 목록 교체는 실제 제거 차이를 보여주기 위해 캐시 기반 비교를 자동 갱신한다. 한 건 파일은 여행지 선택·전체선택 조작을 숨기며, 다건은 기본 포함된 여행지 중 제외할 대상을 고를 수 있다.
5. **선택한 여행지 업데이트:** 최종 버튼을 누르면 변경된 선택을 기존 preview API로 검증하고 해당 선택에 묶인 새 저장 토큰을 자동 발급받는다. 실제 반영 개수·경고·제거 차이를 최종 확인한 뒤 저장한다. 수동 미리보기 재클릭은 필요하지 않다. 검증 실패 시 저장하지 않으며 여행지마다 독립적인 트랜잭션과 저장 직전 충돌 검사를 유지한다.

한국어 원문은 기존 `destination_translations`의 `ko` 행이다. 한국어 복제 필드를 만들지 않는다. `ko.shortDescription`, `ko.description`과 en/ja/zh-CN/zh-TW 각 필드는 독립적이며, 외국어만 선택하면 한국어는 바뀌지 않는다. 없는 언어에 본문만 추가할 때에는 DB의 필수 name을 빈 문자열로 생성하고 미선택 JSON name을 복사하지 않는다. 표시는 기존 언어별 fallback을 사용한다.

업데이트에서도 필드 이름·형식·길이·좌표 쌍·국내/해외 외부 ID·현재 master를 검증한다. 신규 등록의 필수 type/season/region/categories/ko.name은 업데이트에서 누락될 수 있다. 단, `info`를 보낼 때에는 계약을 판별할 기존 type을 함께 지정한다. 여행지 type 및 source_type/external_content_id는 변경하지 않는다. Google Place ID는 기존 해외 계약을 만족하고 다른 여행지와 충돌하지 않을 때만 선택 갱신할 수 있다.

null·누락·빈 문자열·빈 배열은 삭제 요청이 아니다. 미선택 필드는 JSON 값이 있어도 저장하지 않는다. 카테고리/편의시설은 기본 추가 병합이며 **목록 교체**를 선택한 경우만 제거 차이를 보여주고 최종 제거 승인을 받는다. 빈 배열로 전체 삭제하는 기능은 제공하지 않는다. 기존 대표를 제거하면서 새 대표 항목을 선택하지 않으면 저장을 막는다.

자동 추가는 null·공백 문자열·연결 없는 목록만 빈 값으로 판단한다. 숫자 0과 boolean false는 기존값이다. 번역은 표시용 한국어 fallback이 아닌 원시 번역 행을 확인한다. 좌표는 기존 위도·경도가 모두 없을 때만 쌍으로 자동 선택하고, 일부라도 있으면 쌍으로 교체를 확인한다. 카테고리·편의시설의 기존 연결이 있으면 추가 병합 결과를 확인하고 선택한다. `JSON 목록으로 교체(제거 허용)`는 기본 해제다. 업로드·미리보기·선택만으로 DB를 변경하지 않으며 최종 확인 후에만 저장한다.

운영정보는 선택한 유효 필드만 반영한다. 번역 가능한 원문 필드의 ko 정보 번역도 해당 필드만 맞춘다. 단, 원문 자동 추가 시 ko 정보 번역에 다른 기존값이 있으면 덮어쓰지 않고 경고한다. 외국어 운영정보는 언어·필드별로 반영한다. evidence는 미리보기에 표시하며 기존 검증 경고를 재사용한다. 원문 변경 후 기존 외국어를 유지할 때 내용 불일치 경고를 최종 확인해야 한다. JSON/출처 링크만으로 실제 사실을 보증할 수 없으므로 관리자가 내용을 검수해야 한다.

서버 세션의 20분짜리 단일 사용 토큰에 원문·선택·대상·DB 스냅샷·보호 상태를 묶는다. 적용은 잠금 후 현재값·master·중복을 재검증하며 충돌이면 저장하지 않는다. 실패 시 해당 여행지 변경과 보호 기록을 함께 rollback한다. 같은 JSON/선택 재실행의 값이 동일하면 `NO_CHANGE`로 처리한다. 이미지·출처/라이선스/위치, 공개 상태, PK, KTO 연결, 코스·계획·북마크·댓글 참조를 변경하지 않는다.

## 미리보기 성능과 캐시

같은 세션·관리자·JSON 원문과 일치하는 `previewToken`이 있을 때만 파싱·master·매칭 후보·기존값·보호 상태·검증 결과를 재사용한다. 캐시는 파일당 최대 30개 대상과 20분으로 제한한다. 체크박스 변경은 브라우저의 선택과 요약만 갱신하며 DB에 요청하지 않는다. 후보 확정·목록 교체 또는 최종 클릭 시 필요한 선택 검증을 자동 수행해 새 단일 사용 저장 토큰을 발급한다. 선택 변경 전 토큰으로 저장하지 않는다. 다른 JSON·사용자·만료 토큰의 캐시 재사용은 거부한다.

최초 조회는 외부 ID를 출처별로 묶고, 이름 후보는 파일 전체에 하나의 중복 색인을 사용한다. 기존값은 공통 테이블 3회와 유형별 3회 SELECT로 묶고, 보호 기록도 일괄 조회한다. 실제 번역 행을 사용하며 fallback을 적용하지 않는다. 긴 본문의 중복 응답 필드를 제거하고, 접힌 번역·상세 비교의 DOM은 펼칠 때 생성한다.

저장 시 캐시를 폐기하되 다른 여행지의 저장 토큰은 유지한다. 최종 저장은 캐시로 충돌 검사를 생략하지 않고 잠금 후 현재값·보호·master·중복·패치를 다시 검증한다. 저장 또는 충돌 후에는 새 데이터를 읽어 다시 미리본다. 동일값은 선택·패치·새 보호 기록에서 제외한다.

DEV에서 구간별 숫자를 확인하려면 `com.tripbora.service.destinationimport.DestinationImportUpdateService`의 DEBUG 로그를 사용한다. `stageMs`에는 parse/master/validation/resolution/matching/snapshot/protection/diff 소요 시간이 기록되며 JSON 본문은 기록하지 않는다. HTTP `Server-Timing: preview;dur=...`는 서비스 처리 시간이며 직렬화·전송 시간은 포함하지 않는다. 전체 응답 시간·크기와 브라우저 처리 시간은 개발자 도구 Network/Performance에서 별도로 확인한다.

재현 테스트 `DestinationUpdatePerformanceTest`는 실제 Parser/Validator/Resolver/Merge와 DB 경계 mock을 사용한다. `build/reports/destination-json-update-performance/before.json`, `after.json`에 1건·30건의 구간 시간·조회 호출 수·직렬화 시간·응답 바이트를 기록한다. 최초 baseline은 보존하며 이후 실행은 after에 기록한다. 실제 DB·운영 네트워크 성능 측정과 구분해야 한다.

## 요청 대기·오류·저장 결과 확인

버튼 클릭 즉시 `미리보기 처리 중…` 또는 `업데이트 저장 중…`과 경과 시간을 표시한다. 서버 진행률을 추정해서 표시하지 않는다. 10초부터 지연 안내를 표시하며 45초 동안 응답 또는 본문 수신이 완료되지 않으면 브라우저 대기를 종료하고 상태를 복구한다. 이는 DB 트랜잭션 중단을 뜻하지 않는다. 처리 중에는 중복 클릭과 모드 전환을 막는다.

미리보기의 서버·인증·네트워크 오류는 화면에 표시하며 수동으로 다시 요청할 수 있다. 저장의 네트워크 오류·응답 유실·예상하지 못한 서버 응답은 성공 여부가 불확실한 `UNKNOWN`으로 표시한다. 일괄 처리를 중단하고 저장을 자동 재시도하지 않는다. `저장 결과 확인`은 같은 관리자·세션의 기존 토큰으로 결과만 조회하며 DB 조회나 저장을 수행하지 않는다. 서버는 트랜잭션 시작 전에 `RUNNING`, commit/rollback 반환 후 최종 결과를 기록한다. 토큰의 단일 사용 및 충돌 검증은 유지한다.

결과 기록은 세션당 최대 60개·20분이며 서버 재시작이나 세션 만료 뒤에는 보장되지 않는다. 이때는 여행지 관리 화면 링크에서 실제 반영 상태를 확인한 뒤 새로 접속한다. 미확인 저장이 남은 동안 새 미리보기·저장은 차단하며, 단순 실패로 오인한 자동 재저장은 하지 않는다.

브라우저의 요청 번호는 `X-Import-Request-Id`로 전달되고 응답에도 반환된다. Controller의 INFO `request started/finished`와 Service의 DEBUG `stage started/finished`를 같은 요청 번호로 연결한다. 본문·저장 토큰·외부 ID·인증 정보는 로그에 남기지 않는다. `request started`가 없으면 클릭·Network·인증/라우팅부터 확인하고, 시작만 있고 종료가 없는 단계에서 대기 원인을 조사한다. `previewLock`은 캐시 동기화 대기, `saveSnapshotLock`은 저장 직전 잠금 스냅샷 읽기다. 실제 구간 로그를 보려면 DEV에서 해당 Service 로거를 DEBUG로 설정한다.

2026-10-24 조사 환경에는 8081 DEV 서버와 연결 가능한 사용자 브라우저가 없었다. 따라서 실제 사용 중인 요청의 1분 지연 원인이나 DB 대기는 확정하지 못했다. Chrome 테스트는 로컬 HTTP mock에서 Pending·응답 본문 끊김·서버 오류·시간 제한·결과 확인을 검증했으며, MVC 테스트는 실제 Controller와 Service에 mock DB 경계를 연결해 캐시 및 저장 경로를 검증한다. 이 결과를 실제 DEV DB 성능으로 해석하면 안 된다.

## 영속 보호 정책

JSON 보강으로 변경한 필드는 `destination_field_protections`에 기록한다. migration은 사용자의 DEV Spring Boot 실행 시 Flyway가 적용하며, 적용 결과 확인 전에는 schema reference를 갱신하지 않는다.

- `DestinationFieldProtectionService.protect(destinationId, fieldPaths, userId)`는 보강 저장 트랜잭션 내부에서 호출한다. 기존 보호는 해제하지 않고 최초 기록자·시각도 유지한다. 여행지 삭제 시 해당 보호 메타데이터만 FK cascade로 삭제된다.
- 경로는 펼친 JSON 경로다. `translations.ko.shortDescription`과 `translations.ko.description`, `translations.en.description`은 각각 독립적이다. `info.openingHours`, `info.translations.en.openingHours`도 독립적이다. 관계는 `categories`, `mainCategory`, `amenities`처럼 보강 계약의 컬렉션/필드 단위로 기록한다.
- 보호는 값이 빈 문자열, null, false인 경우에도 유효하다. 현재 값의 비어 있음만으로 덮어쓰기 허용 여부를 판단하지 않는다.
- 일반 관리자 수동 편집은 허용한다. `source_type`과 `external_content_id`는 외부 원본의 식별 정보이므로 보호 상태를 나타내기 위해 변경하지 않는다. Wikipedia 판본·저작권을 기록하는 `destination_translation_sources.content_modified`도 재사용하지 않는다.

현재 KTO 여행지 가져오기는 신규 등록 전용이다. `KtoTourBulkImportService.importOne()`은 기존 contentId를 만나면 상세 API 호출과 저장 전에 중복으로 건너뛴다. 관리자 KTO 자동입력은 `create.html`에만 연결되어 있으며 수정 화면에는 없다. 조회 API는 응답만 반환한다. 기존 여행지를 주기적으로 동기화하는 경로는 현재 없다.

향후 KTO 갱신을 추가할 때는 **동일한 저장 트랜잭션에서 `filterKtoPatch(destinationId, proposed)`를 반드시 거친 결과만 저장**해야 한다. `proposed`는 정확한 펼친 경로를 키로 하는 map이며 부모 경로의 중첩 객체를 넘기면 안 된다. 이 서비스는 새 동기화 작업을 실행하거나 기존 관리자 저장을 가로채지 않는다. 새 갱신 구현에서는 JSON 보강과의 동시 저장도 같은 여행지 잠금 규칙으로 직렬화해야 한다.

검증 대상: `DestinationFieldProtectionServiceTest`의 언어·필드 독립성, 보호된 빈 값과 boolean 보존, 중복 경로, 저장 전 전체 경로 검증과 기존 `KtoTourBulkImportServiceTest.alreadyRegisteredContentIdsAreSkippedWithoutCallingTourApi()`의 기존 항목 건너뛰기 동작.
